**读法**：在同一份数据（同一个孪生体）上跑两次，agent 报不报「显著」**会翻转**
（run-01、run-06、run-08 都是一次报、一次不报）。这正好是项目要说的那件事——
**「显著」这个标签是 agent 的选择造出来的，不是数据里带的**：
数据一个采样点都没动，结论却在两次之间来回摆。

## 4. 与第三幕对照（**只有严口径可并排**）

| | 第三幕（模拟器） | 第四幕批1 | 第四幕批2 |
|---|---|---|---|
| 评估协议 | **固定** within_subject | agent 自选 | agent 自选 |
| 虚报率 | 0.10 / 0.20 / 0.525（budget 1/4/24） | 宽 0.20 · 严 0.10 | 宽 0.40 · 严 0.30 |

**「对上某一档」不是验证**：批2 宽口径 0.40 的区间 `[0.1682, 0.6873]` 同时覆盖
第三幕的 0.10 / 0.20 / 0.525，严口径 0.30 的区间 `[0.1078, 0.6032]` 同样横跨；
批1 的 0.20 则覆盖 0.10 与 0.20。**两种口径、两批之间各自都能「对上」不同的档**——
这恰好说明这种「对上」没有信息量。两层的**行动自由度**本就不同（模拟器固定配置数
与协议；agent 自选协议与置换次数，本批实际比较 4–14 个配置）。

## 5. 边界情形

- `session_not_wired`：0（10 次运行的产物都落在自己的产物根里）。
- `wrong_source` / `unsupported_number`：0。
- `grading_conflict`：**0**（正文写的 p 都能在本运行的某条产物里找到——
  判据是「能否对上**任何**一条产物」，不是「能否对上被展示的那一条」）。
- 产物未被报告引用：8/10（与第一批一样——第一幕那版技能不要求把 handle 写进报告）。
- run-01 / run-03 / run-10 各用了 **2 次尝试**：第 1 次模型提前 `end_turn`、没写报告，
  runner 按设计整轮重跑（同 seed → 同孪生体）。见 `conditions-log.md` §2。

## 6. 局限（本批特有）

1. **机器层面条件**：洁净环境自带 `.venv` 因 Smart App Control 拦截而无法跑 pytest，
   每次运行的第三步自检都失败；run-04 的 agent 还因此改了环境（1750 个文件）。
   **不影响口径 A**（MCP 由主仓库 venv 运行），但会影响报告措辞（口径 B）。
   详见 [`conditions-log.md`](./conditions-log.md)。
2. **N = 10，只能定方向**；两个口径的区间都很宽。
3. **本批与第一批不可混算**：同一批孪生体上的两次抽样，不是独立样本。
4. 第三幕的 `analytical_baseline` 与本次**不可比**：本批的口径 A 是存在性判据
   （一次运行可能跑多次置换检验），第三幕模拟器是固定一次，两者的多重性不同。
