# 演示视频分镜与口播稿 · 三幕版（3–5 分钟）

> ⚠️ **绝对不要在视频里念出任何你没有当场跑出来的数字。**
> 本仓库早期版本的分镜里曾有一句编造的「准确率 68%」，而且是被真人念出来的。
> 指南 §13 把「伪造实验数据、运行记录」列为取消资格情形，念数字比写文档更严重。
> 本版全部改为**按屏幕实际输出口播**。

> ℹ️ **配音可以用 AI 生成。** 指南只要求视频「以实际操作为主」，不禁止 AI 配音。
> 但界线要拿准：**声音可以是合成的，画面必须是真实录屏。**
> 用 AI 生成假的界面或拼接未真正跑通的流程，属于伪造运行记录。

> 🔗 **配套**：实际跑法与逐条提示词见 [`docs/runbook-three-acts.md`](runbook-three-acts.md)；
> 本次运行的台账见 `docs/evidence/run-20261002/`。

---

## 总原则

- **全程实操**，不用 PPT 假装。指南明确要求「以实际操作为主」。
- 评委要看的是**闭环**：任务输入 → 执行 → 外部能力调用 → 反馈调整 → 结果验证 → 异常处理。
- 六项要素缺一不可，其中「反馈调整」最容易漏，而它恰是「AGH 与模型执行闭环」占 20% 的得分点。
- 不要加速。Agent 思考时的等待本身就是「在做决策」的证据，可用字幕说明它在看什么。
- **三幕是一条主线**：做工具 → 发现可疑 → 审流程。视频要让评委看懂这条线，
  而不是三个互不相干的片段。

## 三、口播稿（可直接粘贴到 TTS）

> **TTS 使用说明**
>
> 1. 稿子**刻意避开了 E-E-G / C-S-P / M-C-P 这类英文缩写**——中文 TTS 读到夹在中文里的
>    英文常会念错。若要加，请手写成 `E-E-G`、`C-S-P` 这种形式。
> 2. **建议按段落分别生成配音**，再逐段拖到对应画面。整段生成不好对齐，因为工具调用有等待。
> 3. 全文约 830 字，正常语速约 3 分 30 秒；留出等待画面的停顿，正好 4 分半到 5 分钟。
> 4. 「（读屏幕实际值）」是提示你自己看着屏幕念，**不要把括号念出来**。

### 段 ① 开场（0:00–0:25）

这是我们的参赛作品：一个基于 Agnes Harness 的脑电智能体。

它回答一个问题——**一个自己挑分析方法的智能体，它的「显著发现」里，
有多少来自数据，有多少来自它自己挑的这个动作？**

我们用三幕来回答：先做出工具，再发现可疑，最后做实验审这套流程。

### 段 ② 自检（0:25–0:45）

开工前先自检。外部工具已经连上，一共十三个。

我们还跑了一道**盲性验收**——它检查零信号数据和真实数据在元信息上是否无法区分。
这是实验有效性的闸门，不通过，后面所有数字都作废。

（**读屏幕实际值**）

### 段 ③ 第一幕：做工具（0:45–1:30）

第一幕，把工具做出来。

我们只说一段自然语言，要求它先规划。它把计划列成了清单——
这是「智能体」和「脚本」的第一个区别：脚本不会自己写计划。

它没有直接开始分析，而是先做体检：幅值正常吗？有没有坏电极？哪个被试样本太少？
诊断完之后才决定处理方案。

第一轮成绩是（**读实际值**），和瞎猜差不多。于是它换了思路：原来用的特征太粗糙，
还做了全脑平均，把左右的差异抹平了。它改用一种专门为这类信号设计的空间滤波方法，
成绩跳到（**读实际值**）。

**这是整段演示里最关键的地方——这个调整不是脚本写死的，是它看了结果之后自己做的决定。**

### 段 ④ 第一幕：验证（1:30–2:05）

它把两种评估协议都跑了：被试内是（**读实际值**），跨被试是（**读实际值**）。
并且主动说明：跨被试接近随机是这个领域的公认难题，不是实现问题。

还有一点：单次调用装不下三十次打乱重排，它就**分三批各跑十次、再自己合并**——
因为检验的精度下限由次数决定。合并之后，结果是（**读实际值**）。**它没有藏。**

最后和冻结基线对比，结论由服务端计算，它只能引用、不能自己宣称。

### 段 ⑤ 第一幕：异常自愈（2:05–2:35）

我们再给它一个失效的结果编号，看它怎么办。

它拿到了错误码、原因，还有一份可用编号的清单，然后自己换了一个继续跑——
**没有停下来问我**。这就是指南要的「异常处理」。

### 段 ⑥ 第二幕：发现可疑（2:35–3:20）

现在切换角色：从分析员变成审计员。

请注意这一步——报告里的每一个数字都能追溯到磁盘上的一个产物文件，
没有一个是编的。但是，它回头审自己的报告时发现：
**这套配置是看到结果之后才挑出来的**，那个「显著」的判定，没有为「挑」这一步做任何校正。

它把实际比较过的配置和对应的编号逐条列了出来。数字全是真的，
可疑的不是数字造假，而是「**先挑配置、再报数**」这个动作本身。

那这个偏差有多严重？没法靠统计校正推断，**只能做实验测出来**。

### 段 ⑦ 第三幕：审流程（3:20–4:20）

于是有了**零信号试验台**：取真实脑电，在被试内部打乱标签。
脑电一个采样点都没动，只是「哪一段是左手」被抹掉了。它**不是合成数据**，
所以审计层照常放行它产出的数字——这正是要点：**问题不在数字是假的，
在数字全是真的而结论仍然是假的。**

在这个什么都没有的数据上，让机器反复搜索并挑最好的配置，看它报出多少次「显著」。

三档搜索规模跑下来，虚报率是（**读实际值**，对应 0.10 / 0.20 / 0.525）。

搜索规模越大，虚报率越高。而且我们同时跑了爬山法和纯随机两种搜索——
两者没有可辨别的差别。这说明偏差**不依赖搜索的智能性**，
纯粹来自「**取若干次抽样的最大值**」这个动作：一个纯随机搜索，只要跑够次数再挑最好，
同样能造出「显著发现」。

### 段 ⑧ 收尾（4:20–4:50）

我们的作品不是「用 AI 分析脑电」，而是——

**造了一个会自己想办法、并且说真话的实验员；
再用一个零信号试验台，量出它「说真话」的结论里，有多少是它自己挑出来的。**

谢谢。

**剪辑原则（这条界线要拿准）：**

- ✅ **可以剪掉等待和重复**——agent 思考时的空白、加载过程、重复的进度更新
- ✅ **可以跳过中间步骤**，用字幕交代，例如「（此处省略 40 次串行试验，均为同一流程）」
- ✅ 用**字幕补足上下文**，比配音硬撑更清楚
- ❌ **不能拼接出没真正发生的流程**——那是伪造运行记录
- ❌ **不能篡改任何数字或界面内容**

**换句话说：剪掉等待是编辑，编造流程是造假。**

## 七、录制要点

### 7.1 软件选型

| 用途 | 工具 | 说明 |
|---|---|---|
| 录屏 | **OBS Studio**（免费开源） | 多窗口切换、长录制稳定、参数可控 |
| 剪辑 / 配音 / 字幕 | **剪映专业版**（免费） | 中文音色自然、文本朗读、自动打轴 |
| 兜底 | Windows `Win+G` 游戏栏 | 零安装，但**只能抓单个窗口**，浏览器↔终端切换会断，长录制不稳，仅应急 |

> 不要用手机拍屏幕。不要用录屏软件的「加速」功能——加速后的流程会让评委怀疑中间跳了什么。

### 7.2 OBS 参数（一次配好）

| 位置 | 设置 |
|---|---|
| 设置 → 视频 | 基础(画布) 1920×1080，输出 1920×1080，FPS **30** |
| 设置 → 输出 → 录像格式 | **mkv**（崩溃不损坏；录完「文件 → 重新封装录像」转 mp4） |
| 设置 → 输出 → 编码器 | 有独显选 NVENC H.264，否则 x264；速率控制 **CQP**，CQ 20–22 |
| 来源 | 一个「显示器采集」即可；想更清晰再加两个「窗口采集」（浏览器 / 终端），用场景切换 |
| 音频 | 麦克风**静音**——配音是后期 AI 朗读，现场收音只会带进杂音 |
| 快捷键 | 设「开始 / 停止录制」快捷键，避免每次点界面 |

1080p30 录静态界面，每小时约 100–300 MB，三小时约 1 GB 上下，不必压缩画质。

### 7.3 分段录制（**不要一口气录三小时**）

每幕存一个文件，命名与分镜对齐：

```
01-P0自检+P1第一幕.mkv
02-P2第二幕.mkv
03-P3a-budget1.mkv
04-P3b-budget4.mkv
05-P3c-budget24-hill.mkv
06-P3d-budget24-random.mkv
07-P4收尾.mkv
```

两个理由：中途崩溃不会全丢；剪辑时直接按幕对齐分镜表。

budget=24 那两段各 60–90 分钟，两种做法都行：**全程挂着录**（最省事），
或**只在开头、结尾、超时重试那一次开录**，中间用字幕交代「此处省略 N 次串行试验」。
**分段是编辑，拼接没发生的流程才是造假。**

### 7.4 开录前的屏幕准备（五分钟，省掉后面反复重录）

- 显示分辨率 1920×1080；浏览器缩放 **110–125%**，否则评委看不清工具返回值
- 关掉通知（Win11「专注助手」），关掉无关标签页和书签栏
- 鼠标指针在「辅助功能 → 鼠标指针」里调大、调成黑色
- **翻 MCP 设置页和会话时留意别露 API Key**——AGH 的 provider 配置页会显示密钥，
  录到就整段废掉
- **数据必须提前缓存好**（见 §一），视频里不要等下载

### 7.5 剪辑与配音流程

1. OBS 录完 → mkv 重新封装成 mp4
2. 剪映导入 → 按 §二 分镜表剪
3. 配音：用剪映「文本朗读」**按口播稿分段生成**再逐段对齐——整段生成对不齐，
   因为工具调用有等待
4. 加字幕 → 导出 1080p
5. 口播稿里标「（**读屏幕实际值**）」的地方，念的时候照着屏幕念，**别念成预期值**

### 7.6 不可逾越的红线

- 出现错误分支时**不要剪掉**，那是评分项
- **一镜到底**：Agent 的推理过程应当是实时的。若中途卡死，如实重录，
  不要用剪辑掩盖，更不要事后补录一段「看起来跑通了」的片段
- 不要露 API Key、邮箱、学号
- **剪辑只能删等待，不能造流程**

## 八、关于稳定性

模型当天的表现无法预先保证。因此：

- 保留一条**确定性基线路径**（`eeg_ablation` 里的基线），它一定能出结果，
  但**绝不能把它当作 agent 的输出呈现**。
- 万一模型当场卡住或绕圈，这本身是可以说明的，前提是你有 fallback 并且讲清楚。
  但不要用剪辑把一次失败的运行伪装成成功。
- **如果某条线不顺，砍掉它保证整体流畅。** 六要素里「异常处理」和「结果验证」
  是硬要求；`todo` 规划那条属于加分项，可以舍弃。
- 第三幕耗时最长、最容易被超时打断。**超时重试本身是可展示的异常处理**，
  但要如实说明，不要假装一次跑完。
